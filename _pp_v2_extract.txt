Implementierung

Das Problem                                                       Technische Besonderheit: Index-basierte Pools

                                                                  gross der Datensatz.

Die 4 Query-Strategien:

   "Bei 196 Klassen divergieren die drei Uncertainty-Maße: Least Confidence und Margin betrachten nur Top-1/Top-2,
   Entropy nutzt die gesamte Posterior-Verteilung."

Strategie         Formel                  Intuition

Least Confidence  1 - max_c P(y=c|x)      Wie unsicher ist das Modell bei seiner
                                          Top-1 Klasse?

Margin            P_top1 - P_top2         Wie nah liegen die zwei
                                          wahrscheinlichsten Klassen?

Entropy           -sum_c P_c * log(P_c +  Wie verteilt ist die Unsicherheit über
                  epsilon)                alle Klassen?

Random            --                      Baseline -- kein
                                          Informationskriterium
Technische Architektur -- Streamlit-Constraints,
Threading-Modell, Zustandsmaschine

Das Kernproblem: Streamlit ist zustandslos, Streamlit re-rendert das gesamte Script bei jedem User-
Klick. Das bricht naiv implementierte ML-Pipelines:

Problem                                     Lösung im Projekt

Worker-Thread stirbt bei Reload             @st.cache_resource  Controller als Prozess-
                                            Singleton

UI blockiert beim Training                  Daemon-Thread trennt Training von UI-Thread

Keine Live-Updates ohne Blocking            Adaptives Polling via @st.fragment

 Mutable State nicht thread-sicher          Alle Writes unter threading.Lock, UI liest nur
                                            Snapshots
Das Zwei-Thread-Modell:

·"Event Inbox (Worker  UI): immutable Event-Dataclass, Version-Counter  Fragment zieht nur neue Events"
·"Command Queue (UI  Worker): plain dicts, non-blocking get_nowait() -- blockiert nie den UI-Thread"

ML-Kern: Transfer Learning & Fine-Tuning

Modell-Laden via TIMM

· Einheitliche API für ResNet, MobileNet, EfficientNet
· Feature-Dimension: model.num_features -- automatisch ermittelt
· Embeddings via Forward-Hook auf model.global_pool -- keine Architektur-Änderung nötig

Freeze  Unfreeze Strategie

Phase / Zyklus                              Was passiert

 Zyklus 1, Ep. 1­freeze_epochs               Backbone eingefroren -- Head trainiert sich sicher ein
 Zyklus 1, danach                            Backbone aufgetaut + Optimizer neu gebaut (Adam-State für alle Params)
 Zyklus 2+ (continue)                        Gewichte behalten -- nur Optimizer-State und LR-Schedule reset

Discriminative Learning Rates

Backbone = 0.1× LR, Head = 1.0× LR -- pretrained Features stabil halten, Head schnell lernen lassen.

Standard -- schnell, stabil                 Feature-Qualität maximieren   Klassifikation + Struktur

Supervised Contrastive Loss -- Idee & Implementierung

  Idee: Embeddings gleicher Klasse zusammenziehen, verschiedener Klassen abstoßen -- im gesamten Batch,
  nicht nur paarweise.

· Features L2-normalisiert  Kosinus-Ähnlichkeit
· Samples ohne positives Pair im Batch werden übersprungen
· Besonders relevant bei AL: frühe Zyklen haben wenige Labels pro Klasse -- SupCon

    profitiert von Klassen-Balance im Batch

ProjectionHead -- nur für SupCon (kein Query/Eval)

· Ein einziger Forward Pass für CE + SupCon via global_pool-Hook -- kein doppelter Durchlauf
· ProjectionHead wird nicht für Query oder Evaluation genutzt -- nur für den Loss

Experimente Setup

Dataset           Stanford Cars -- 196 Klassen
Train / Test      ~8.000 / ~8.000 (offizieller Split)
Modell            ResNet-50 (ImageNet-pretrained)
Initial Pool      500 (stratified, 1/Klasse)
Query-Batch       100 pro Zyklus
Zyklen            30
Epochen / Zyklus  20
Loss              combined: (1-)·CE + ·SupCon
Seed              42
Hardware          NVIDIA H100 PCIe, JupyterHub-Cluster

"Vergleich: 4 AL-Strategien (Entropy, Margin, Least Confidence, Random) + voll-überwachte
Referenz auf dem gesamten Trainings-Split (200 Epochen, sonst identische Konfiguration)."

Ergebnisse -- 4 Strategien, 30 Zyklen, Stanford
Cars

· Entropy > Margin > Least Confidence > Random -- Reihenfolge wie bei 196 Klassen erwartet
· AL-Strategien mit 56% der Labels erzielen 68% der voll-überwachten Accuracy
· AL-Läufe besser kalibriert als Supervised-Baseline (ECE 0.16 vs. 0.19) -- Temperature Scaling wirkt stärker bei

     kleinen Pools.

Fazit & Thesis-Beiträge

Was wurde gebaut:

· Voll funktionsfähige interaktive Active-Learning-Pipeline (PyTorch + Streamlit)"
· 4 Query-Strategien, 3 Loss-Modi, 3 Modell-Architekturen -- alle konfigurierbar zur

      Laufzeit
· Ergebnis-Dashboard: Learning Curves, UMAP-Evolution, ECE, Konfusionsmatrix, Run-

      Vergleich

Thesis-Beiträge:

· Empirisch -- Uncertainty-Sampling schlägt Random auf Stanford Cars; AL-Läufe
     besser kalibriert als Supervised-Baseline trotz geringerer Accuracy

· Architektonisch -- Entkoppeltes Zwei-Thread-Design: SupCon, UMAP, ECE
     nachträglich integriert ohne eine Zeile UI-Code zu ändern

· Didaktisch -- Interaktives Tool macht AL-Zyklus, Unsicherheitsmaße und
     Kalibrierung visuell nachvollziehbar
